# Internationalization (i18n)

BirdDex uses [next-intl](https://next-intl.dev) with URL-based locales (`/en/...`, `/uk/...`). Every page route lives under `app/[locale]`, including the root layout (fonts, `AppHeader`, Ask Robin chat). `/collection` and `/signup` were removed entirely — both were dead redirect stubs with no real UI (Google OAuth handles sign-up and login through the same flow). `/auth/callback` (a Route Handler, not a page) intentionally stays outside `[locale]` since it's a fixed OAuth redirect target. See `docs/specs/i18n-ukrainian.md` for the original scope decision.

## Key files

- `i18n/locales.ts` — supported locales (`en`, `uk`) and the default locale.
- `i18n/routing.ts` — next-intl's `defineRouting()` config, used by the proxy middleware.
- `i18n/navigation.ts` — locale-aware `Link`, `usePathname`, `useRouter` from `createNavigation()`. Use these instead of `next/link` / `next/navigation` in any component rendered under `app/[locale]` (which, in practice, is nearly everything — see below).
- `i18n/request.ts` — loads the message dictionary for the active locale on the server.
- `app/[locale]/layout.tsx` — the app's root layout (fonts, `<html>`/`<body>`, `AppHeader`, `AskRobinChatProvider`). Wraps everything in `NextIntlClientProvider`, so any client component anywhere in the tree can call `useTranslations`/`useLocale`/the navigation hooks.
- `messages/en.json`, `messages/uk.json` — translation dictionaries, one JSON object per locale with matching key structure.
- `proxy.ts` — for any path without an `/en` or `/uk` prefix (except `/auth/*`, which must stay unprefixed), hands off to next-intl's middleware for locale detection/redirect. Once a path has a locale prefix, it falls through to the existing Supabase session-refresh/login-redirect/admin-guard logic, now matched with locale-aware regexes (e.g. `/^\/(en|uk)\/admin(\/|$)/`).
- `shared/ui/LanguageSwitcher/LanguageSwitcher.tsx` — rendered in `AppHeader`, under the logo. Deliberately does **not** use next-intl's hooks (`useLocale`, `@/i18n/navigation`'s `usePathname`); it parses the locale directly off `next/navigation`'s `usePathname()` instead. This was needed while some routes were still unmigrated and lacked `NextIntlClientProvider` — now that everything is migrated it could use the next-intl hooks directly, but there's no need to change it.

## Adding a new translated string

1. Add the key to **both** `messages/en.json` and `messages/uk.json`, nested under a namespace matching the page/feature (e.g. `"HomePage": { "title": "..." }`).
2. In a **Server Component**, call `const t = await getTranslations('Namespace')` (from `next-intl/server`) and use `t('key')`.
3. In a **Client Component**, use `useTranslations('Namespace')` (from `next-intl`) and `t('key')`.

Most UI strings across the app are still hardcoded English (only the home page title/description are translated so far) — extracting them into `messages/*.json` is ongoing follow-up work, not yet done route-by-route.

## Navigation and links

Since every route is under `app/[locale]`, always use `Link`/`useRouter`/`usePathname` from `@/i18n/navigation` (not `next/link`/`next/navigation`) for links between pages — pass plain, un-prefixed paths (e.g. `href="/locations"`) and it resolves to the current locale automatically.

Exceptions:
- `app/auth/callback/route.ts` and anything redirecting to it must use fixed, non-locale-prefixed URLs (Supabase's OAuth redirect target is fixed). The one exception inside that flow is `signInWithGoogleAction`'s redirect to Google's own OAuth URL — that's an absolute external URL, so it uses plain `next/navigation`'s `redirect` (aliased `redirectExternal`), not next-intl's.
- `revalidatePath` calls for dynamic routes use the pattern form, e.g. `revalidatePath('/[locale]/birds/[id]', 'page')`, since the literal un-prefixed path no longer exists as a real route.

`requireAuth()`, `requireAdmin()`, `signInWithGoogleAction`'s OAuth-error path, and `logoutAction` all redirect with the caller's actual locale: they read it via `getLocale()` (from `next-intl/server`, request-scoped, populated by `setRequestLocale()` in the root layout) and pass it to `redirect()` from `@/i18n/navigation`. `i18n/navigation.ts` re-exports `redirect`/`getPathname` alongside `Link`/`usePathname`/`useRouter` for this reason. `proxy.ts`'s auth/admin guard redirects run before `NextIntlClientProvider` mounts, so they instead read the locale straight off the already-prefixed pathname (`en`/`uk` capture group, falling back to `routing.defaultLocale`) and build the redirect URL manually.

Because next-intl's `redirect()` isn't typed as returning `never` (unlike `next/navigation`'s), TypeScript won't narrow types after calling it — follow it with an explicit `return`/`throw` when the surrounding code relies on narrowing (see `requireAuth`/`requireAdmin`).

## What's out of scope today

- Only the home page's title/description are translated. All other UI text (nav labels, buttons, empty states, forms) is still hardcoded English on both `/en` and `/uk` — extracting these into `messages/*.json` is the next phase of work.
- Bird catalog content (`name_eng`, `name_latin`, `field_note`, habitat/food/behaviour labels) lives in Supabase, not in the message JSON files, and is not translated. Translating it requires a data-model change (translated columns or a separate translations table), not just UI string work.
- `docs/app-guide.md` and the Ask Robin `APP_GUIDE` prompt (`features/bird-guide/bird-guide-prompt.ts`) are English-only and not part of this i18n effort.
